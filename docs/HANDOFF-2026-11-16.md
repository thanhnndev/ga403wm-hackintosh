## 1. The project in one paragraph

ASUS ROG Zephyrus G14 GA403WM (Ryzen AI 9 HX 370, Radeon 890M, RTX 5060, 2880x1800 120 Hz OLED) running macOS
Tahoe 26.7.2 (25G332, Darwin 25.6) under OpenCore. The goal is a full hardware port, not workarounds: the 890M drives
the display and all apps through our own source build of NullMoth's `NMXGPU` (a port of Linux amdgpu on a LinuxKPI /

powered off (Eco). Around that: native MT7925 Wi-Fi/Bluetooth, audio, sleep (s0ix), ASUS controls (RogControl app +
AsusWmi), a hypervisor (RyzenHV, for Docker). The owner uses the machine daily: video + Claude + Docker together is
the normal load and the baseline for every measurement.

## 4. The work stream that just ran: NMXGPU wired memory (Steps 141-142)

Problem (2026-11-10, out-22): 9.98 GB wired 35 min after boot. `zprint` by tag: NMXGPU 3412 MB against 1440 MB really
in use; IOSurface 1404 MB; Reserved 1719, PTE 530, PMAP 317.

Two causes, both in our xkpi layer (`bsdcompat/src/nmx_page.c`, `xnu/nmx_mm.cpp`, patch
`patches/amdgpu-userptr-park.patch`, `patches/ttm-pool-cap.patch`):

- **The chunk pool never shrank.** Single pages come from 2 MB chunks; freed pages went to one global list, so chunks
  could never be returned, and TTM's own pool was uncapped because xnu never fires `vm_lowmem`.
- **Imported IOSurfaces stay wired for the life of their GPU buffer** (`surf_wire()` prepares the surface's descriptor
  until the BO is destroyed), used or not.

Builds, in order. Each "fix" exposed the next problem in video playback:

| Build | Change | Result |
|---|---|---|
| out-23 | Step141: per-chunk free lists, release an empty chunk above a 64 MB reserve; TTM pool cap 128 MB | NMXGPU tag 1818 MB vs 1482 live (was 3412 vs 1440). Video 21 drops / 60 s (out-22: 7): release/refill churn |
| out-26 | Step141b: release only after 5 s unused, reserve 256 MB. Step142: park (unwire) IOSurface BOs idle 10 s, re-wire on next use | 666 MB unwired, 0 failures. Video 38 drops: parked swap-chain surfaces re-wired in a burst, and allocation bursts > reserve made 165 chunks in the GPU path |
| out-26, park off | A/B | run 1: 0 drops; run 2: 142 (pool shrank in the pause between runs, 107 chunks made inline) |
| out-27/28 | Step141c prefill thread call; Step141d 60 s peak floor; Step142b park after 60 s | build checks only |
| **out-29 (live)** | + Step141e: two-window peaks, 10 min slow peak (cap 512 MB), 1 GB cap, slow sweep | boot OK: 703 chunks prefilled, 1 inline. Video (light load, RTX powered, no Docker): 0 and 10 drops / 60 s, 0 chunks made inline. Re-wire results not in yet |

Sysctls to read: `debug.nmx_pages_live`, `nmx_page_chunks`, `nmx_page_free`, `nmx_page_chunks_freed`,
`nmx_page_chunks_filled`, `nmx_page_chunks_inline`, `nmx_page_hwm`, `nmx_userwire_*`, `nmx_surfwire_*`,
`nmx_userwire_parked*`, `nmx_userwire_parks/unparks/unpark_fail`, `nmx_upin_*`, `nmx_park_*`,
`nmx_userptr_park_ms` (RW; 0 turns the park off live). Boot-arg `nmxpark=0` disables parking.

Open, to verify on out-29:
- video: drops ≤ 7 / 60 s at Chrome 1080p60 maximised, `chunks_inline` ≈ 0 during playback, two runs with a pause;
- park re-wire: video paused > 60 s then resumed, Mission Control (the owner must look at the thumbnails), tab switching
  after > 60 s idle; no GPU fault / timeout lines;
- `zprint -t` (root) at ~35 min uptime, same load, against the out-22 numbers above;
- total wired under daily load (Docker running).

**A fresh look is warranted here.** Five builds in one evening chased video drops caused by our own allocator policy.
Questions worth asking before building out-30: is a pool that returns memory needed at all if the IOSurface park does
the big saving; should chunk memory be allocated pageable/purgeable or come from the kernel's own page allocator
instead of our 2 MB chunks; does Linux/FreeBSD LinuxKPI have a shrinker hook we can drive from xnu's memory-pressure
notification (`vm_pressure` / `kern.memorystatus_vm_pressure_level`) instead of timers; and is the drop count on a
YouTube page even a trustworthy signal (see 5.1).

for the new main, none started: (a) Docker Desktop's memory limit (owner setting, instant); (b) RyzenHV mapping guest
memory lazily / pageable instead of wiring it at map time, or unwiring pages the guest has not touched; (c) balloon /
free-page reporting from the Linux guest; (d) 24 vCPUs for the VM (~5.2 cores busy) is also the owner's setting.
